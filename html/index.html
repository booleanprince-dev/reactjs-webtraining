01 / YOUR OPENING POSITION

Lead with judgement, not libraries.

In an architecture interview, state the system boundary and the trade-off before naming a tool. You want to sound like someone who can keep a product moving as complexity grows.

“I design React applications around ownership of state, independent feature boundaries, accessible behavior, and safe delivery. I put server data in a query cache, URL-shareable state in the router, local interaction state in components, and introduce a global client store only for genuinely shared workflows.”

02 / STATE PLACEMENT

The decision that prevents most React complexity.

Before selecting Redux—or any state library—classify the state by its owner and lifecycle. The state manager should follow that answer.

SERVER

Backend owns truth

Orders, profiles, permissions, inventory.

TanStack Query / RTK Query
URL

Browser history owns it

Search, page, selected tab, sort.

React Router params
LOCAL

A subtree owns it

Form draft, open dialog, hover, input.

useState / useReducer
WORKFLOW

Client crosses features

Toast queue, offline draft, multi-step flow.

Redux Toolkit / Zustand
INTERVIEW ANSWER

“I use Redux Toolkit when cross-feature client state has complex transitions, needs predictable debugging, or must survive route changes. I do not use it as an HTTP cache by default; TanStack Query or RTK Query handles server state better.”

Rule of thumb Derived state has no owner. Compute visibleOrders; do not store it and create another source of truth.

03 / APP ARCHITECTURE

Organize by capability, not file type.

A feature owns its API adapter, model, UI, orchestration, and tests. The app layer composes features. Shared code is domain-agnostic and may not depend back on a feature.

src/
 ├─ app/                  # providers, router, composition
 ├─ features/
 │   └─ orders/
 │      ├─ api/           # request/response adapters
 │      ├─ components/    # feature UI
 │      ├─ hooks/         # feature orchestration
 │      ├─ model/         # types, schemas, domain rules
 │      └─ state/         # only when truly warranted
 └─ shared/
     ├─ api/  components/  lib/

Boundary rules

  1. Features can consume shared; shared cannot consume features.
  2. Map raw API shapes at the API boundary.
  3. Expose a small public surface per feature.
  4. Extract abstractions after stable duplication emerges.

04 / SERVER STATE

Async work is a state machine.

Initial loading, failure, successful empty data, successful data, and background refetching are distinct user experiences. Do not replace useful data with a full-page spinner while it refreshes.

Initial fetch

Show a purposeful skeleton/status indicator. The user has no trustworthy content yet.

Request failed

Explain what failed in useful language, preserve recoverable input, log context, and offer Retry.

Canonical result

Render data or an intentional empty state. Never conflate an empty list with a request failure.

Existing data is stale

Keep visible content and add a subtle refreshing status. Cache identity must include every response-affecting filter.

const ordersQuery = (filters) => queryOptions({
  queryKey: ['orders', filters],
  queryFn: ({ signal }) => ordersApi.list(filters, signal),
  staleTime: 30_000,
});

05 / QUALITY & SCALE

Architecture includes the unhappy path.

01

Type boundaries

Use strict TypeScript, discriminated unions for workflows, and Zod to validate untrusted runtime data.

02

Accessible behavior

Semantic elements, keyboard flows, focus management, meaningful async announcements.

03

Measured performance

Profile first. Then fix the actual bottleneck: data, bundle, render churn, CPU, or DOM size.

04

Behavioral tests

Use Testing Library + MSW for observable state transitions; keep E2E for critical journeys.

Performance answer to rehearse

“I start with the browser performance tools, React Profiler, Web Vitals, network waterfall, and bundle analysis. I diagnose whether it is API latency, JavaScript cost, render churn, expensive computation, or DOM size. Then I make and verify a measured improvement—rather than memoizing by instinct.”

06 / HANDS-ON CHALLENGE

Build an Order Operations Console.

Timebox yourself to 2–3 hours. Narrate the state ownership decisions as you build.

Product brief

Operations users search orders, filter by status, inspect an order, and update its status. A filtered URL must be shareable. The API is eventually consistent after an update.

StackReact · TypeScript · Router · TanStack QueryOutcomeA resilient vertical slice
Reveal the expected walkthrough

1. URL: filters are shareable navigation state, so the router owns them.

2. Query: orders belong in a query cache because the backend owns their truth.

3. Dialog: selection and draft status stay in local state.

4. Mutation: invalidate ['orders']; favor canonical refetch over optimistic complexity until UX evidence says otherwise.

5. Feedback: use a global toast queue only if it crosses routes or multiple features.

BUILD-ALONG / COMPLETE ANSWER

Build it from an empty folder.

Follow the steps in order. Each one is a working, explainable increment—the way a lead should plan a feature slice.

Step 1 Create the React + TypeScript project

Use Vite for a lean client build, then install only the tools that match the ownership model.

npm create vite@latest order-ops -- --template react-ts
cd order-ops
npm install
npm install react-router-dom @tanstack/react-query zod
npm install -D vitest @testing-library/react @testing-library/jest-dom msw jsdom

Why: Router owns shareable location state; TanStack Query owns server state; Zod validates runtime data. Do not install Redux yet—the brief has no cross-feature client workflow.

Step 2 Create the feature boundary and domain model

Create src/features/orders/{api,components,hooks,model}, then add model/order.ts:

export type OrderStatus = 'pending' | 'processing' | 'fulfilled' | 'cancelled';
export interface Order { id: string; reference: string; customerName: string; totalCents: number; status: OrderStatus; updatedAt: string; }
export interface OrderFilters { q: string; status?: OrderStatus; page: number; }
export interface OrderPage { items: Order[]; page: number; totalPages: number; }

Say: “These are our domain types, not proof that the API is trustworthy. I validate network data at the boundary next.”

Step 3 Configure Router and Query once

Put application-wide dependencies near the root.

// src/app/providers.tsx
const client = new QueryClient({ defaultOptions: { queries: { retry: 1, refetchOnWindowFocus: false } } });
export function AppProviders({ children }: PropsWithChildren) {
  return <QueryClientProvider client={client}>{children}</QueryClientProvider>;
}

// src/main.tsx
createRoot(document.getElementById('root')!).render(
  <StrictMode><BrowserRouter><AppProviders><OrdersPage />
  </AppProviders></BrowserRouter></StrictMode>
);

Why: 30 seconds is just an example stale-time policy. Explain that freshness is a product decision, not a magic number.

Step 4 Validate and translate the API boundary

Components should never own fetch details. Validate external data before it enters the feature.

const orderSchema = z.object({
  id: z.string(), reference: z.string(), customerName: z.string(),
  totalCents: z.number().int().nonnegative(),
  status: z.enum(['pending', 'processing', 'fulfilled', 'cancelled']), updatedAt: z.string(),
});
const pageSchema = z.object({ items: z.array(orderSchema), page: z.number(), totalPages: z.number() });

export async function listOrders(filters: OrderFilters, signal?: AbortSignal): Promise<OrderPage> {
  const params = new URLSearchParams({ q: filters.q, page: String(filters.page) });
  if (filters.status) params.set('status', filters.status);
  const response = await fetch(`/api/orders?${params}`, { signal });
  if (!response.ok) throw new Error(`Could not load orders (${response.status})`);
  return pageSchema.parse(await response.json());
}
Step 5 Make query keys and mutations explicit

A query key is cache identity; include every input that changes the response.

export const orderKeys = { all: ['orders'] as const,
  list: (filters: OrderFilters) => ['orders', filters] as const };

export function useOrders(filters: OrderFilters) {
  return useQuery({ queryKey: orderKeys.list(filters),
    queryFn: ({ signal }) => listOrders(filters, signal),
    placeholderData: keepPreviousData, staleTime: 30_000 });
}
export function useUpdateOrderStatus() {
  const client = useQueryClient();
  return useMutation({ mutationFn: ({id, status}) => updateOrderStatus(id, status),
    onSuccess: () => client.invalidateQueries({ queryKey: orderKeys.all }) });
}

Why invalidate? The API is eventually consistent. Refetching canonical data is safer than optimistic complexity until latency and conflict behavior prove it necessary.

Step 6 Put filters in the URL and render async states

The screen coordinates owners. The hook fetches; the page handles visible behavior; temporary editing state stays local.

const [params, setParams] = useSearchParams();
const filters = { q: params.get('q') ?? '', status: params.get('status') as OrderStatus | undefined,
  page: Math.max(1, Number(params.get('page') ?? '1')) };
const { data, isPending, isFetching, isError, error, refetch } = useOrders(filters);
const [selected, setSelected] = useState<Order | null>(null);

if (isPending) return <p role="status">Loading orders…</p>;
if (isError) return <section role="alert">{error.message} <button onClick={() => refetch()}>Retry</button></section>;
// show an empty state when data.items.length === 0
// retain the list and show “Refreshing…” when isFetching is true

Interview point: initial load and background refresh are different. Preserve useful content while refreshing.

Step 7 Build the semantic list and local status editor

Use a real table for tabular data. In production, prefer a tested accessible dialog primitive for focus handling.

<tbody>{data.items.map(order => <tr key={order.id}>
  <td>{order.reference}</td><td>{order.customerName}</td><td>{order.status}</td>
  <td><button onClick={() => setSelected(order)}>Update status</button></td>
</tr>)}</tbody>

Step 8 Test behavior and deliver the explanation

Use MSW at the network boundary; test what a user can observe, not hook internals.

it('offers retry when the list request fails', async () => {
  server.use(http.get('/api/orders', () => HttpResponse.error()));
  render(<OrdersPage />);
  expect(await screen.findByRole('alert')).toHaveTextContent('Could not load orders');
  await userEvent.click(screen.getByRole('button', { name: 'Retry' }));
});

30-second answer: “The URL owns filters; the query cache owns orders; the dialog owns temporary state. Query keys include filters, schemas protect the API boundary, and mutations invalidate canonical data. I test each observable async state. I would add Redux only for a shared client workflow such as offline drafts or a cross-route notification queue.”

07 / INTERVIEW DRILLS

Say the answer out loud.

How do you choose Context, Redux, and TanStack Query?

Classify ownership first. Context distributes stable dependencies or small subtree state. Redux Toolkit handles complex shared client workflows. Query tools handle backend-owned data. The URL handles shareable navigation state.

How would you structure a growing React application?

Feature boundaries, dependency direction, explicit public APIs, and a small app-composition layer. Centralize platform conventions, not every component.

How do you lead code review?

Prioritize correctness, security, behavior, architecture, and coverage before style. Make comments actionable, teach judgement, and encode recurring feedback into tooling and conventions.

How would you plan this in Linear?

Create thin vertical slices with acceptance criteria, identify risks and dependencies, record decisions, and use milestones to track outcomes rather than activity.
