01 / THE STACK MAP

Start with a small, well-owned foundation.

There is no universal React stack. These are common, well-supported choices; a senior engineer explains why one applies to the product in front of them.

Core principle: tools should reinforce ownership boundaries. Server-owned data needs a query cache. Shareable state belongs in the URL. Local interactions stay local. Add a global store only for a real shared client workflow.

03 / ENGINEERING PRACTICES

Make change cheap for the next engineer.

01 / STATE

Classify before you store.

Keep derived values derived; colocate interaction state; put filters and pagination in the URL; reserve query libraries for server state; add Redux only when multiple features genuinely coordinate a client-owned workflow.

02 / BOUNDARIES

Organize by product feature.

A feature owns its components, query hooks, API adapters, model, and tests. shared/ must not depend on product features. Map raw API shapes at the boundary so backend changes do not leak through the UI.

03 / COMPONENTS

Compose small behavior units.

Give each component one main reason to change. Prefer composition over prop flags that multiply combinations. Use controlled forms where validation and inter-field behavior need it; do not reflexively over-control simple inputs.

04 / EFFECTS

Use effects to synchronize with external systems.

An effect is not a default place for data fetching or derived calculations. Fetch through the query layer; calculate during render; put subscriptions, browser APIs, and imperative widgets in effects with correct cleanup.

05 / PERFORMANCE

Measure before optimizing.

Use the React Profiler, browser performance tools, Web Vitals, network waterfall, and bundle analysis. Fix the bottleneck you find: server latency, oversized bundle, expensive render, unstable props, or a too-large DOM. Memoization is a targeted tool, not a style rule.

06 / DELIVERY

Make the safe path the easy path.

Use type checks, linting, unit/integration tests, review, CI, preview environments, feature flags for risk, and post-release telemetry. Write a small ADR when a choice has durable consequences.

04 / QUALITY BASELINE

Non-negotiables for a production feature.

TYPE SAFETY

Validate at runtime

Enable strict TypeScript. Use schema validation at API boundaries. Model workflow states with discriminated unions so invalid combinations are hard to represent.

ACCESSIBILITY

Ship usable behavior

Start with semantic HTML, keyboard support, visible focus, correctly named controls, dialog focus management, and announcements for meaningful async updates.

SECURITY

Protect the real boundary

The server authorizes actions. The UI may hide unavailable controls for user experience, but client guards are not access control. Treat user-provided HTML as untrusted.

OBSERVABILITY

Know what happens after release

Capture unexpected errors, Web Vitals, high-value mutation failures, and correlation IDs—without leaking sensitive data into client logs.

05 / THE INTERVIEW VERSION

Answer in architecture, not packages.

“For a React product, I start by placing state according to its owner. The URL owns shareable navigation state; a query cache owns remote data; components own transient interaction state; and a store such as Redux Toolkit is reserved for complex cross-feature client workflows. I organize by feature, validate data at API boundaries, test observable async behavior, and use telemetry and safe delivery practices to make change reliable. Libraries follow those constraints—not the other way around.”

Choose the smallest stack that makes the right boundaries obvious.
